## 1. P0 详情

### BE-01 steer 在四条退出路径上都可能丢失

- **位置**：`services/pidAgent/agentLoop.mjs:122-124`（只在回合开始 drain）、`:175-177`（纯文本 → 内层结束）、`:246-254`（内层结束直接 break）
- **四个丢消息的出口**：

  | 出口 | 位置 | 是否丢 | 后果 |
  |---|---|---|---|
  | 模型返回纯文本后退出 | `:246-254` | 丢 | 最后一次纠偏无人接收 |
  | `maxTurns` 兜底 | `:223-226` | 丢 | 实测：`maxTurns=2` → 残留 1 条 |
  | `shouldStopAfterTurn` 达标收敛 | `:235-243` | 丢 | 实测：残留 1 条；**"达标提示/安全回退通知"正是走 steerQueue** |
  | `signal.aborted` | `:127-130` | 丢 | 会话已终止，丢失无可观察影响（仅一致性问题） |

- **实测**：
  ```
  A maxTurns=2:      stopReason=max-turns  steer 残留=1  messages=6
  B shouldStop:      stopReason=stop       steer 残留=1  messages=3
  C 纯文本退出:      LLM 可见消息不含 steer  steer 残留=1
  ```
- **修复**：抽一个统一的排空函数，**在所有退出点前**调用（不要只在"内层结束"补一处）：
  ```js
  // 退出前：把已排队但未注入的消息落进对话
  const drainBeforeExit = () => {
    const pending = [...steerQueue.drain(), ...followUpQueue.drain()]
    for (const m of pending) messages.push(m)
    return pending.length
  }
  ```
  对 `max-turns` / `shouldStop` / 纯文本三个出口：drain 后若非空，`continue outerLoop` 让模型处理；对 `aborted` 出口只 drain 不重启（保留在 `result.messages` 便于上层展示）。
  `max-turns` / `shouldStop` 的额外重启用 `forcedRestartUsed` 限一次（防止"安全通知持续产生 → 排空又重启"的循环）；纯文本出口不设预算（只有用户真的排了新消息才会重启）。
- **验收**：`tests/pid-agent-loop.mjs` 增 4 例——三种出口后 `steerQueue.size()===0` 且 `result.messages` 含 steer 文本；followUp 仍能重启外层。

### BE-02 重试退避不可中断

- **位置**：`services/pidAgent/llm.mjs:143-149`
- **现象**：`await new Promise(r => setTimeout(r, delay*1000))` 不与 signal 竞争，abort 检查在其之后。
- **实测**：abort 后耗时 **2004~2014ms** 才返回 `{ok:false, error:'请求已中止'}`；退避表 `[0,2,4,8,16]` 最坏档要等满 16s。
- **修复**：可中止的 sleep，并在 await 后立即检查 signal：
  ```js
  const sleep = (ms, signal) => new Promise((resolve) => {
    if (signal?.aborted) return resolve()
    const done = () => { clearTimeout(timer); signal?.removeEventListener('abort', done); resolve() }
    const timer = setTimeout(done, ms)
    signal?.addEventListener('abort', done, { once: true })
  })
  ```
- **验收**：abort 后 `Date.now()-t0 < 200ms`。

### BE-04 串口下发失败被完全吞掉（工具假成功）

- **位置**：`components/PidAgentPanel.vue:17-23`、`composables/usePidAgent.mjs:699-701`、`services/pidAgent/tools/index.mjs:229` 与 `:328`
- **现象链**：
  1. `onSerialSend` 调 `window.electronAPI.serial.send(line,'utf8')`，**不 return、不 catch**；
  2. `controller.sendSerialCommand = async (cmd) => { await onSerialSend?.(cmd) }` → await 的是 `undefined`；
  3. 工具层立即 resolve，返回 `message: '参数已下发到设备（PID 指令）'`；
  4. 串口已断时（`serial.js:291` 抛 `串口未打开`）产生 renderer 未捕获 rejection。
- **影响**：串口模式下模型按"参数已生效"的错误前提继续调参（与代码注释记载的"无论怎么调反馈都一样"属同一类事故）；`emit('send', line.length)` 还按字符数而非字节数计数。
- **修复**：
  ```js
  onSerialSend: (cmd) => {
    const line = String(cmd ?? '').endsWith('\n') ? String(cmd) : `${cmd}\n`
    emit('send', new TextEncoder().encode(line).length)
    return window.electronAPI?.serial?.send?.(line, 'utf8')
  }
  ```
  工具层捕获后返回 `{ ok:false, mode:'serial', error, message:'下发失败，参数未生效' }`（`set_pid_params` / `set_target` 两处）。
  策略工具 `run_pid_strategy` 同步识别该结果，新增 `serial_send_failed` 状态并在提示词中说明（避免模型误以为参数已生效）。
- **验收**：断开串口后调用 `set_pid_params`，toolResult 含 `ok:false`；控制台无 unhandled rejection。

### BE-05b 停止后护栏仍会把回退参数下发到真实设备（新增）

- **位置**：`usePidAgent.mjs:624-650`（`notifySamplesCollected` 无 `running` 守卫）、`:654-657`（`serialCollector` 在停止时未复位）、`:870-886`（`onSerialData` 无 `running` 守卫）、`:640-647`（回退参数经 `onSerialSend` **真实下发**）
- **链路**：用户点"停止" → `abortController.abort()`，但 `serialCollector.active` 仍为 true → 12s 窗口继续收样 → 窗口满 → `notifySamplesCollected` → 护栏判定超调/振荡 → `setPid` + `buildPidCommand` + `onSerialSend` → **设备参数被改写**（同时 UI 在"已停止"状态下又冒出一条 `[安全机制]` 消息）。
- **实测（已复现触发链）**：
  ```
  第1轮良好 status=STABLE  → 护栏记录 bestStable
  停止后窗口仍完成= true samples=41
  第2轮 status=OVERSHOOTING overshoot=120
  停止后护栏 triggered= true rollbackPid={"kp":1,"ki":0,"kd":0}   ← 会被下发到设备
  ```
- **判据**：`onAcceptancePassed`（`:726`）有 `!running.value` 守卫，说明这条路径属于**漏加**而非有意设计。
- **修复**（三处，缺一不可）：
  1. `notifySamplesCollected` 首行加 `if (!ctx.alive() || !running.value) return`（实测按此实现；仿真模式的采集也在运行中发生，统一守卫即可，无需按模式分支）；
  2. `stopAgent()` 内 `serialCollector?.reset()` + `safetyGuard?.reset()`，并给 `createSerialStepCollector` 增加 `reset()`（`active=false`、`samples=[]`）；
  3. BE-10（`onSerialData` 未运行即返回）作为前置条件。
- **验收**：串口模式启动 → `set_target` → 窗口开启中停止 → 继续灌 15s 数据 → 断言无 `[安全机制]` 消息、`serial.send` 调用次数为 0。

## 2. P1 详情

### BE-03 4xx 全量重试

- **位置**：`llm.mjs:165-169`（`if (!res.ok) { ...; continue }`）
- **实测**：401 共发出 5 次请求，耗时 ≈30s。
- **修复（已实现）**：只对 `408/409/425/429/5xx` 与网络异常重试（`RETRYABLE_STATUS` + `isRetryableStatus`）；4xx 立即返回可读文案（401 → "API Key 无效或已过期"，404 → "接口或模型不存在，请检查 baseUrl 与 model"）。`WorkspaceAnalysis.vue:181` 的"AI 解释"同样受益。实测 401 由 5 次请求 / ≈30s 降到 1 次 / < 1s。

### BE-05 会话状态串台（代际号不足）

- **位置**：`usePidAgent.mjs:195-209`（`dataBuffer`/`steerQueue`/`followUpQueue`/`safetyGuard`/`serialCollector`/`sessionClock`/`abortController` 全是 composable 级 `let`）、`:556-590`（`startAgent` 整体替换）、`:706`（`getDataBuffer: () => dataBuffer`）
- **为什么要改**：代际号只能保护 `running` 与 UI 消息流；对**闭包读取外层变量**的路径无效：
  - `controller.getDataBuffer()` 返回的是**新会话**的缓冲；
  - `notifySamplesCollected` 把护栏消息推进**新会话**的 `steerQueue`；
  - `controller.isStopped()` 读的是**共享** `abortController` → 重启后旧会话的工具看到"未中止"，策略工具会继续执行；
  - `setPidHandler` 写的是**共享** `currentPid`。
- **修复**：会话状态收进 `startAgent` 内的 `ctx` 对象，controller/tools/回调全部闭包捕获 `ctx`：
  ```js
  function createSessionContext() {
    return {
      seq: ++sessionSeq,
      dataBuffer: createDataBuffer({ acceptance }),
      steerQueue: createPendingMessageQueue(),
      followUpQueue: createPendingMessageQueue(),
      abortController: new AbortController(),
      safetyGuard: null, serialCollector: null,
      sessionClock: 0, serialStartTime: null,
      pid: { ...initialPid }, target: 0, ff: {}
    }
  }
  // 所有对外入口先校验：if (ctx.seq !== activeCtx?.seq) return
  ```
  代际号作为配套（`emit` / `onSerialData` / `finally` 三处校验）。
- **验收**：停止后立刻重启，旧会话的任何工具调用不改变新会话的缓冲/参数/队列；`running` 不被旧 promise 复位。

### BE-06 缓冲饱和后 push 退化（量化）

- **位置**：`dataBuffer.mjs:117-124`、`:131-162`
- **实测**（`capacitySec=600 / maxSamples=60000`；不同 Node/机器上为 2.1~3.0s）：

  | 场景 | 20k 次单条 push | 单次成本 |
  |---|---|---|
  | 未饱和（首次填充 60k） | 20ms | ≈0.34µs |
  | 饱和后（持续替换） | **2109~2963ms** | ≈105~148µs |

- **影响**：串口 1kHz 下约 60s 进入饱和，此后每帧搬 6 万个指针，常驻约 10% 单核（渲染线程）。
- **修复**：摊还淘汰 —— 条数超 `sampleLimit + 5%`、或时间跨度超 `capacity + max(0.2s, 2%)` 时一次性清理；条数/时间因此都是**软上限**（最多超出 5%）。后续可换环形缓冲进一步消除「突发批量淘汰」。修复后同机实测：**20k 次 push 9ms**（原 2109~2963ms）。

### BE-08 `send()` 无超时

- **位置**：`serial.js:290-326`
- **修复**：`Promise.race([writePromise, timeout(1500)])`，超时 reject 中文错误并推送一次 `serial:error`。

### BE-09 LLM 代理边界（拆成两档）

- **位置**：`main/index.js:87-115`、`services/llmTransport.mjs:15-38`
- **立即可做（零副作用）—— 已实现于 `src/main/llmProxy.js`**：
  1. 仅允许 `https://`（`http://localhost|127.0.0.1` 例外），其余直接拒绝；
  2. `redirect: 'error'`，杜绝 https → http 降级泄露 Key；
  3. 流式读 body，累计超过 `MAX_RESPONSE_BYTES`（建议 8MB）立即 abort；
  4. 透传 `timeoutMs`（当前 `llmTransport` 从不传，恒走 120s 默认）。
- **另议（原方案有缺陷）**：**host 白名单不能由 payload 里的 `baseUrl` 推导** —— 那等于让发起方自证清白。要做需在主进程新增 `llm:configure`，由用户显式确认后缓存 host；同时注意自建/局域网模型端点会被误伤，`localhost` 例外只覆盖一部分。
- **验收**：`http://` 外网地址被拒；重定向到 http 的地址被拒；9MB 响应体返回可读错误而非卡死；`timeoutMs` 生效（把模型指向黑洞地址，30s 内返回超时）。

### BE-11 `maxPoints` 无上限

- **位置**：`tools/index.mjs:145`、`dataBuffer.mjs:215`
- **实测**：`maxPoints: 1e9` → 返回 6 万点 / **1.58MB** 单条 toolResult。
- **修复**：schema 加 `minimum: 2, maximum: 500`；实现侧 `clamp(finite(maxPoints,30), 2, 500)`。

### BE-13 `onBeforeLlm` 抛错导致无声结束（修法已修正）

- **位置**：`agentLoop.mjs:133-136`、`:74-116`
- **⚠ 原方案错误**：直接 `try { outerLoop } finally { emit(agent_end) }` 会**重复发射** —— `:155`（aborted）、`:160`（error）、`:257`（正常）已经各发一次；`usePidAgent.mjs:400-411` 对每条 `agent_end(error)` 都推一条错误消息，UI 会出现两条。
- **正确修法（已实现）**：**收敛为单一发射点**。
  ```js
  let endEmitted = false
  const emitEnd = async () => {
    if (endEmitted) return
    endEmitted = true
    await emitEvent({ type: 'agent_end', stopReason, turnCount: turn, usage, ...(endError ? { error: endError } : {}) })
  }
  // 三处早退改为 break（不再单独 emit），循环外包 try/catch/finally：finally { await emitEnd() }
  ```
  `onBeforeLlm` 单独 try：压缩失败上报 `compaction_error` 并继续（UI 只提示一次），不中断调参。
- **验收**：mock 一个抛错的 `onBeforeLlm`，断言 `agent_end` 只发 1 次且 `stopReason='stop'`；LLM 失败路径同样只发 1 次（已加入 `pid-agent-loop.mjs` 第 16~18 例）。

### BE-23 `settlingTime` 为 O(n²)（提级 + 修法已修正）

- **位置**：`controlAnalysis.mjs:55-66`（`samples.slice(i)` + `.every()`，每个 i 都复制一次尾部）
- **⚠ 原方案错误**：加"早退阈值"会改变判定语义（可能返回错误的调节时间）。**严格等价的 O(n) 写法**是反向扫一次：
  ```js
  function settlingTime(samples, stepIndex, finalTarget, stepSize, bandRatio) {
    const band = Math.max(Math.abs(stepSize) * bandRatio, 1e-6)
    const tailMin = samples.length - 3            // 原实现要求 tail.length >= 3
    let lastOut = -1
    for (let i = samples.length - 1; i >= stepIndex; i -= 1) {
      if (Math.abs(samples[i].feedback - finalTarget) > band) { lastOut = i; break }
    }
    if (lastOut < 0) return 0                     // 全程在带内 → 原实现返回 0
    if (lastOut >= tailMin) return null           // 末 3 点内仍越界 → 窗口内未进入稳定带
    return samples[lastOut + 1].t - samples[stepIndex].t
  }
  ```
- **实测（振荡未收敛，是调参失败时最常见的形态）**：

  | 样本数 | 耗时 | 状态 |
  |---|---|---|
  | 12,000 | 76ms | OSCILLATING |
  | 30,000 | **1699ms** | OSCILLATING |
  | 60,000（外推） | ≈6.8s | 渲染线程同步阻塞，波形/表格一起卡死 |

  注：v1.0 给出的 39.6ms@12000 点取自**斜坡**形态（每个 i 的首元素立即越界，`.every()` 立即返回），不代表最坏情况。
- **修复**：上述反向扫描；顺带把 `:300-303`、`:340-343` 的 `Math.max(...arr)` 改为显式循环，消除 >20 万元素时的 RangeError 风险（实测 `Math.max(...200000)` 抛 `Maximum call stack size exceeded`）。
  另外把阶跃后的「极值 / 输出峰值 / RMSE / 过零点」合并为一次遍历，去掉 4 个 3~6 万元素的中间数组：30k 点从 58ms 再降到 **38ms 冷 / 17ms 热**，60k 点 29ms。
- **验收**：`settlingTime` 已导出，`tests/control-analysis-settling.mjs` 用改前的朴素实现逐例比对 46 组输入（结果完全一致）+ 30k 点 < 50ms + 6 万点不抛栈。
