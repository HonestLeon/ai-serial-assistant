## 1. 项目概述

AI 串口调试助手是一款桌面应用（MIT 协议），在传统的串口调试工具基础上引入 AI 能力。早期定位是通用嵌入式调试，当前重点面向**高校竞赛学生（电赛 / 智能车 / RC / RM 等）**，主打两条特色能力：**AI 辅助分析数据** 与 **AI 辅助调参（辅助式，人工确认下发）**。

**技术栈：**

| 层级 | 技术 | 版本 |
|------|------|------|
| 桌面框架 | Electron | ^42.5.1 |
| 前端框架 | Vue 3 | ^3.5.39 |
| UI 组件库 | Element Plus | ^2.14.2 |
| 图表库 | ECharts | ^6.1.0 |
| 串口通信 | serialport + @serialport/parser-readline | ^13.0.0 |
| 构建工具 | electron-vite + Vite | ^5.0.0 / ^7.3.6 |
| 打包工具 | electron-builder | ^26.1.0 |

**核心功能模块：**
- 串口配置与连接（端口/波特率/数据位/停止位/校验位/流控 + DTR / RTS 控制）
- 数据流监控（Rx/Tx 实时收发、文本/HEX 切换、毫秒时间戳、录制回放）
- 实时波形图（`WorkspaceChart`：ECharts 8 通道 I0–I7、滚动窗口 2000 点、通道显隐切换、CSV/JSON 导出）
- 波形分析（`WorkspaceAnalysis`：本地确定性响应指标 + 通道特征统计 EDA + AI 结构化解释 + 报告导出）
- AI 助手（`AiPanel` + `WorkspaceAnalysis`/`PidPanel` 内的结构化调用：OpenAI 兼容 API，支持 gpt-4o-mini / gpt-4o / deepseek-chat / qwen-turbo）
- PID 辅助调参（`PidPanel`：策略注册表 + 本地候选 + AI 解释 + 人工二次确认 + 导出 .c/.h）
- 控制响应模拟（无需硬件，离线体验完整链路）
- 明暗双主题

## 2. Electron 是什么

Electron 是一个用 **网页技术（HTML/CSS/JavaScript）开发桌面应用程序** 的开源框架。它把一个浏览器内核（Chromium）和一个 Node.js 运行时打包进同一个桌面程序里。

> Electron = 一个永不关闭的 Chromium 浏览器 + 一个 Node.js 运行时。

本项目用它的原因：串口调试工具需要直接访问电脑的串口硬件，纯网页做不到；而 Electron 让开发者可以用熟悉的 Vue 3 + ECharts 写界面，同时通过 Node.js 调用底层硬件能力。典型 Electron 应用还包括 VS Code、Discord、Slack、Figma 桌面端等。

## 3. 前端与后端：主进程就是「后端」

一个常见误区是认为「Electron 和 Vue 3 都是前端工具，那后端用什么」。

关键点：**Electron 的主进程本身就是后端**，不需要单独部署服务器。

- **Vue 3**：纯前端框架，只管界面显示与交互。
- **Electron**：不是前端工具，而是应用容器，内部同时包含：
  1. **Chromium**（浏览器内核）→ 负责跑 Vue 3 这套前端界面
  2. **Node.js**（完整服务端运行时）→ 这就是「后端」

本项目的「后端」就是 `src/main/` 下的 Node.js 代码，语言就是 JavaScript/Node.js，运行在用户本机，没有云端服务器、不需要联网（AI 调用除外）。

**类比：**

| 传统 Web 应用 | Electron 应用 |
|------|------|
| 浏览器（前端）← HTTP → 服务器（Java/Python/Node） | Vue 界面（前端）← IPC → 主进程（Node.js，本机运行） |

## 4. 后端代码剖析

### 4.1 `src/main/index.js` —— 后端入口（相当于服务器启动文件）

```js
import { app, shell, BrowserWindow, ipcMain } from 'electron'
import { join } from 'path'
import { listPorts, openPort, closePort, send, setDtr, setRts } from './serial.js'
```

- **创建窗口**（第 8–40 行）：`new BrowserWindow(...)` 把 Chromium 窗口造出来，把 Vue 界面塞进去；安全策略在此设置：`contextIsolation: true`、`nodeIntegration: false`。
- **开发模式自动开 DevTools**（第 25–27 行）：当以 `electron-vite dev` 启动时，`process.env['ELECTRON_RENDERER_URL']` 存在，`isDev` 为 `true`，窗口 ready 后自动 `mainWindow.webContents.openDevTools({ mode: 'detach' })`（独立窗口）。
- **注册 IPC 接口**（第 47–54 行）——后端暴露的「API 接口」：
  ```js
  ipcMain.handle('ping',              () => 'pong')
  ipcMain.handle('serial:list',       () => listPorts())
  ipcMain.handle('serial:open',       (_, options) => openPort(mainWindow, options))
  ipcMain.handle('serial:close',      () => closePort(mainWindow))
  ipcMain.handle('serial:send',       (_, data, encoding) => send(data, encoding))
  ipcMain.handle('serial:setDtr',     (_, value) => setDtr(value))
  ipcMain.handle('serial:setRts',     (_, value) => setRts(value))
  ipcMain.on('console:log',           (_, level, msg) => console.log(prefix, msg))  // 渲染进程日志回传主进程
  ```
  渲染进程不能直接打开串口，只能调用 `serial:open` 这类「接口名」，由主进程真正操作硬件后返回结果。思想与 Express 的 `app.get(...)` 一致，只是通信通道从 HTTP 换成了 IPC。`serial:setDtr` / `serial:setRts` 用于 MCU 的 DTR / RTS 引脚控制（如 Arduino 复位、RS485 收发切换）。

> 注：`_` 是约定俗成的占位参数，代表「事件对象」此处用不到。

### 4.2 `src/main/serial.js` —— 真正的业务逻辑（相当于后端控制器）

- **模块级状态**（第 4–6 行）：`currentPort` / `currentParser` / `currentOptions` 保存当前连接，相当于后端的「内存状态」。
- **列举串口**：`await SerialPort.list()` 调用系统 API 枚举硬件，对应前端「刷新端口列表」。
- **双协议解析引擎**（核心差异点）：
  - **Raw 模式**（默认）：按行读取文本，前端用正则提取数字。`currentPort.pipe(new ReadlineParser({ delimiter: '\n' }))` 表示按换行符分包。
  - **JustFloat 模式**：二进制四字节浮点帧。尾帧标识 `0x00 0x00 0x80 0x7F`，用 `parseJustFloat(buf)` 把字节流解析成浮点数组（第 85 行 `if (protocol === 'justfloat')` 分支）。
  - 收到数据时反向推给前端：
    ```js
    win.webContents.send('serial:data', {
      raw: line,
      hex: Buffer.from(line).toString('hex'),
      time: Date.now(),
      protocol: 'raw' | 'justfloat'
    })
    ```
    `webContents.send('serial:data', ...)` 即后端 → 前端的「推送」（类似 WebSocket 的 server push）。
- **发送数据**：把前端发来的字符串按编码转成字节流写入硬件，纯 Vue 做不到：
  ```js
  const buffer = encoding === 'hex'
    ? Buffer.from(data.replace(/\s/g, ''), 'hex')   // HEX 模式：转二进制
    : Buffer.from(data, 'utf8')                      // 文本模式
  currentPort.write(buffer, ...)
  ```
- **DTR / RTS 控制**（第 167–172 行）：`setDtr(value)` / `setRts(value)` 直接设置串口控制信号线电平，供前端「DTR / RTS」按钮调用。

## 5. 安全桥梁：Preload

### 5.1 `src/preload/index.js` —— 前后端之间唯一的门

主进程规定 `nodeIntegration: false`，即前端界面碰不到 Node.js。前端要调串口，只能通过 preload 这个安全桥梁。

```js
import { contextBridge, ipcRenderer } from 'electron'

const api = {
  ping: () => ipcRenderer.invoke('ping'),
  log:  (level, msg) => ipcRenderer.send('console:log', level, msg),
  serial: {
    list:    () => ipcRenderer.invoke('serial:list'),
    open:    (options) => ipcRenderer.invoke('serial:open', options),
    close:   () => ipcRenderer.invoke('serial:close'),
    send:    (data, encoding) => ipcRenderer.invoke('serial:send', data, encoding),
    setDtr:  (value) => ipcRenderer.invoke('serial:setDtr', value),
    setRts:  (value) => ipcRenderer.invoke('serial:setRts', value),
    onData:    (callback) => ipcRenderer.on('serial:data',   (_, payload) => callback(payload)),
    onStatus:  (callback) => ipcRenderer.on('serial:status', (_, payload) => callback(payload)),
    onError:   (callback) => ipcRenderer.on('serial:error',  (_, message) => callback(message))
  }
}

contextBridge.exposeInMainWorld('electronAPI', api)
```

- `ipcRenderer.invoke('serial:open')` = 前端「打电话」给后端，字符串必须和主进程 `ipcMain.handle('serial:open', ...)` 完全一致（一对暗号）。
- **两个方向的方法有区别：**
  - `list/open/close/send/setDtr/setRts/ping` 用 `invoke`（前端主动问，后端答，有返回值）；
  - `onData/onStatus/onError` 用 `on`（后端主动推，前端被动收），对应 `serial.js` 里的 `webContents.send(...)`。
- `contextBridge.exposeInMainWorld('electronAPI', api)` 把这个 `api` 对象安全地挂到浏览器 `window` 上，于是前端可用 `window.electronAPI.serial.xxx`。
- **只暴露白名单里的 11 个方法，别的什么都碰不到** —— 这就是「最小暴露面」的安全设计（不暴露整个 `ipcRenderer`）。

### 5.2 `src/renderer/src/components/SerialPanel.vue` —— 前端如何使用接口

- **刷新端口列表**：`ports.value = await window.electronAPI.serial.list()`
- **打开/关闭串口**：把界面上选的参数打包发给后端 `open(...)`，由 `serial.js` 真正打开硬件。
- **DTR / RTS 控制**：调用 `window.electronAPI.serial.setDtr(value)` / `setRts(value)`。
- **监听后端推送**：`window.electronAPI?.serial?.onStatus?.(...)` 和 `onError`，对应反向通道，用于更新绿点 / 「已连接」文字。

**完整链路：**

```
前端 SerialPanel.vue ──invoke──▶ preload ──IPC暗号──▶ 主进程 index.js
   (window.electronAPI.serial.open)        (ipcRenderer)      (ipcMain.handle)
                                                  │
                                          serial.js: new SerialPort() 真正打开硬件
                                                  │
                               webContents.send('serial:status'/'data')
                                                  ▼
                                        preload: onStatus/onData
                                                  ▼
                                          前端回调 → 更新 UI / 画波形
```

## 6. 数据如何变成波形

### 6.1 `src/renderer/src/components/WorkspaceChart.vue`

> 早期版本的 `ChartPanel.vue` 已被本组件取代；本文以当前实际挂载的组件为准。

- **订阅数据流**（第 258 行）：`window.electronAPI?.serial?.onData?.(appendData)` 把 `appendData` 注册成回调，每来一行数据就调一次。
- **从文本抠数字**（第 50 行 `extractNumbers`）：
  ```js
  function extractNumbers(text) {
    // 取 ":" 之后的一段，再按正则提取数字，最多前 8 个 → I0~I7
    const body = String(text).includes(':') ? String(text).split(':')[1] : String(text)
    const matches = body.match(/[-+]?\d*\.?\d+/g)
    return matches ? matches.slice(0, 8).map(Number) : []
  }
  ```
  一行 `12.5 3.2 8.0` → `[12.5, 3.2, 8.0]`，对应 README「每行数据通过正则提取数字」。
- **数字塞进通道队列**（第 157 行 `appendData`）：
  ```js
  function appendData(payload) {
    const values = extractNumbers(payload.raw)
    if (values.length === 0) return
    samples.value.push({ label: formatTime(), values })   // 一条采样 = { 时间标签, 各通道值 }
    if (sampleLabels.value.length > MAX_POINTS) samples.value.shift()  // 超 2000 丢最旧
    renderChart()
  }
  ```
  - `samples` 是采样数组，每个元素 `{ label, values }`，`values[i]` 即第 `Ii` 通道当前值；
  - **`MAX_POINTS = 2000` + `shift()` = 滚动窗口 FIFO 队列**：只保留最新 2000 个采样，旧的从左被挤掉，波形从右往左滚动（不同于早期 `ChartPanel` 的 200 点）；
  - 归一化绘制（Y 轴按通道分别缩放便于同屏对比），但 CSV/JSON 导出时保留原始真值。
- **ECharts 画成曲线**：X 轴是采样时间下标，Y 轴是数值，`visibleChannels` 控制哪条线显示（点眼睛图标切换），`dataZoom` 支持框选缩放平移，`animation: false` 保证高频刷新流畅。主题随 `theme-change` 事件在明暗间切换。

### 6.2 `src/renderer/src/components/DataMonitor.vue`

同样独立监听 `serial:data`，把数据以文本日志形式显示（Rx/Tx 方向、时间戳），并内置**控制响应模拟**（二阶欠阻尼模型，dt = 50 ms，输出 `CTRL: <目标> <反馈> <控制量> <误差>`，用于离线验证链路）。即「一份串口数据，多处消费」：

| 消费方 | 用途 |
|------|------|
| `WorkspaceChart` | 画实时波形 |
| `DataMonitor` | 文本日志 + 控制响应模拟 |
| `WorkspaceAnalysis`（经 props 传入 `channelHistory`） | 波形分析、响应指标、EDA |
| `PidPanel`（经 props 传入 `channelHistory`） | 调参采样 |

**数据变波形全景：**

```
设备发来 "12.5 3.2 8.0\n"
   │  主进程 ReadlineParser 分行 + send('serial:data')
   ▼
WorkspaceChart.appendData(payload)
   ├─ extractNumbers → [12.5, 3.2, 8.0]
   ├─ samples.push({ label, [12.5, 3.2, 8.0] })   （超 2000 则 shift）
   ▼
renderChart()  →  ECharts 重绘折线
   ▼
屏幕出现随时间向右推进的实时波形
```

## 7. AI 能力如何调用大模型

本项目的 AI 调用分两类：**自由对话**（`AiPanel` 内）与**结构化解释**（`WorkspaceAnalysis` / `PidPanel` 内触发）。二者都直连 OpenAI 兼容接口，不经过主进程。

### 7.1 `AiPanel.vue` —— 自由对话客户端

**关键前提：这一块完全不依赖 IPC / 主进程。** 它是渲染进程直接用浏览器原生 `fetch` 去请求大模型服务商服务器，自己就是一个标准 ChatGPT 风格客户端，和串口、主进程毫无关系。

- **配置来源**：`apiKey` / `baseUrl` / `model` 直接存在浏览器 `localStorage`。默认值 `https://api.deepseek.com`、`deepseek-chat`。因为 Base URL 可配，gpt-4o-mini / gpt-4o / deepseek-chat / qwen-turbo 等任意 OpenAI 兼容接口都能用（改 Base URL 即可，协议完全一致）。
- **发送消息 + 构造请求**：
  ```js
  const response = await fetch(`${config.baseUrl}/chat/completions`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${config.apiKey}`
    },
    body: JSON.stringify({
      model: config.model,
      messages: messages.value.map(m => ({ role: m.role, content: m.content })),  // 整段历史
      stream: false
    })
  })
  ```
  - 请求地址 = `Base URL + /chat/completions`（OpenAI 聊天补全标准路径）；
  - 鉴权 = `Authorization: Bearer <API Key>`；
  - `messages` 传入**整个对话历史**，所以模型有记忆、能理解上下文；
  - `stream: false` = 整段生成完再一次性返回。
- 快捷操作（数据分析 / 异常诊断 / 协议解析 / 发送指令）已接入预设 `prompt`，「发送指令」会真正调用串口下发；其余通过预设提示词引导模型。

### 7.2 结构化调用 —— 把串口数据喂给 AI

早期版本里 AI 与串口数据是「断联」的：自由对话时模型看不见波形。现已通过 `services/controlAnalysis.mjs` 的 `buildStructuredAiContext(...)` 打通：

- **`WorkspaceAnalysis.requestAiExplanation()`**：把本地算出的**响应指标卡**（上升/稳定时间、超调率、稳态误差、RMSE、稳态波动）+ **通道特征统计 EDA**（均值/峰值/方差等）打包成结构化上下文，连同安全 system prompt（禁止改边界、禁止声称控硬件）一起发给模型，得到「为什么超调」「往哪调」的解释。无 API Key 时降级为本地提示文本，离线可用。
- **`PidPanel` 调参**：`buildPidSuggestion` 生成有界候选参数后，同样经 `buildStructuredAiContext` 带上结构化上下文 fetch AI，但 **AI 只解释、不直接改参数**，最终仍由人工二次确认下发。

> 注意边界：自由对话（`AiPanel`）仍是纯文字，模型看不到波形；只有 `WorkspaceAnalysis` / `PidPanel` 触发的解释才会自动注入结构化上下文。这是「离线优先、安全可控」设计的一部分。

## 8. 数据主线总结

| 主线 | 路径 | 经过主进程？ |
|------|------|------------|
| 串口配置/收发 | Vue → preload → IPC → serial.js | ✅ 是 |
| 波形绘制 | 主进程 `serial:data` → WorkspaceChart 提取 → ECharts | ✅ 是 |
| 数据日志 | 同上 → DataMonitor 显示文本 | ✅ 是 |
| 波形分析 | `serial:data` → props → WorkspaceAnalysis 本地算法 +（可选）AI | ✅ 是（AI 部分否） |
| **AI 自由对话** | **Vue 直接 fetch 云端，不经过 IPC** | ❌ 否 |

> 一句话：**串口链路（配置→收发→波形→分析→日志）已端到端打通，是一条完整的 Electron 三进程架构；AI 模块以「本地确定性算法为主、云端大模型为辅（仅解释）」的形态嵌入，且默认离线可用。**

- **`.c/.h` 导出**：生成的控制器代码里 `output_min / output_max` 写死 `-100~100`，未读取策略的 `outputLimit`，嵌入前需按执行器量程修改。
- **下发指令依赖固件约定**：调参下发的 `PID kp ki kd` 字符串依赖 MCU 侧解析，目前尚无统一参考固件，是「自动调参闭环」唯一依赖外部约定的环节。
- **版本号不一致**：`App.vue` 顶部显示 `v1.1.0`，但 `package.json` 的 `version` 仍为 `1.0.0`，打包产物版本会与界面显示对不上，建议统一。
