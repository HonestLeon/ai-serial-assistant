# AI 串口调试助手 · 原理解析文档

> 本文档基于源码逐文件阅读整理，用于帮助理解这个 Electron + Vue 3 桌面应用的工作原理。
> 涉及文件：`README.md`、`src/main/index.js`、`src/main/serial.js`、`src/preload/index.js`、`src/renderer/src/components/SerialPanel.vue`、`ChartPanel.vue`、`DataMonitor.vue`、`AiPanel.vue`。

## 1. 项目概述

AI 串口调试助手是一款面向嵌入式开发、硬件调试场景的桌面应用（MIT 协议），在传统的串口调试工具基础上引入 AI 能力。

**技术栈：**

| 层级 | 技术 | 版本 |
|------|------|------|
| 桌面框架 | Electron | ^42.5 |
| 前端框架 | Vue 3 | ^3.5 |
| UI 组件库 | Element Plus | ^2.14 |
| 图表库 | ECharts | ^6.1 |
| 串口通信 | serialport | ^13.0 |
| 构建工具 | electron-vite + Vite | ^5.0 / ^7.3 |
| 打包工具 | electron-builder | ^26.1 |

**核心功能模块：**
- 串口配置与连接（端口/波特率/数据位/停止位/校验位/流控）
- 数据流监控（Rx/Tx 实时收发、文本/HEX 切换、毫秒时间戳）
- 实时波形图（ECharts 8 通道 I0-I7、滚动窗口 200 点、通道显隐切换）
- AI 助手（OpenAI 兼容 API：GPT-4o / DeepSeek / 通义千问）
- 通道数值面板、明暗双主题

## 2. Electron 是什么

Electron 是一个用 **网页技术（HTML/CSS/JavaScript）开发桌面应用程序** 的开源框架。它把一个浏览器内核（Chromium）和一个 Node.js 运行时打包进同一个桌面程序里。

> Electron = 一个永不关闭的 Chromium 浏览器 + 一个 Node.js 运行时。

本项目用它的原因：串口调试工具需要直接访问电脑的串口硬件，纯网页做不到；而 Electron 让开发者可以用熟悉的 Vue 3 + ECharts 写界面，同时通过 Node.js 调用底层硬件能力。典型 Electron 应用还包括 VS Code、Discord、Slack、Figma 桌面端等。

## 3. 前端与后端：主进程就是「后端」

一个常见误区是认为「Electron 和 Vue 3 都是前端工具，那后端用什么」。

关键点：**Electron 的主进程本身就是后端**，不需要单独部署服务器。

- **Vue 3**：纯前端框架，只管界面显示与交互。
- **Electron**：不是前端工具，而是应用容器，内部同时包含：
  1. **Chromium**（浏览器内核）→ 负责跑 Vue 3 这套前端界面
  2. **Node.js**（完整服务端运行时）→ 这就是「后端」

本项目的「后端」就是 `src/main/` 下的 Node.js 代码，语言就是 JavaScript/Node.js，运行在用户本机，没有云端服务器、不需要联网。

**类比：**

| 传统 Web 应用 | Electron 应用 |
|------|------|
| 浏览器（前端）← HTTP → 服务器（Java/Python/Node） | Vue 界面（前端）← IPC → 主进程（Node.js，本机运行） |

## 4. 后端代码剖析

### 4.1 `src/main/index.js` —— 后端入口（相当于服务器启动文件）

```js
import { app, shell, BrowserWindow, ipcMain } from 'electron'
import { join } from 'path'
import { listPorts, openPort, closePort, send } from './serial.js'
```

- **创建窗口**（第 8–40 行）：`new BrowserWindow(...)` 把 Chromium 窗口造出来，把 Vue 界面塞进去；安全策略在此设置：`contextIsolation: true`、`nodeIntegration: false`。
- **注册 IPC 接口**（第 47–52 行）——后端暴露的 4 个「API 接口」：
  ```js
  ipcMain.handle('serial:list',  () => listPorts())                              // 列举串口
  ipcMain.handle('serial:open',  (_, options) => openPort(mainWindow, options))  // 打开
  ipcMain.handle('serial:close', () => closePort(mainWindow))                    // 关闭
  ipcMain.handle('serial:send',  (_, data, encoding) => send(data, encoding))   // 发送
  ```
  渲染进程不能直接打开串口，只能调用 `serial:open` 这类「接口名」，由主进程真正操作硬件后返回结果。思想与 Express 的 `app.get(...)` 一致，只是通信通道从 HTTP 换成了 IPC。

> 注：`_` 是约定俗成的占位参数，代表「事件对象」此处用不到。

### 4.2 `src/main/serial.js` —— 真正的业务逻辑（相当于后端控制器）

- **模块级状态**（第 4–6 行）：`currentPort` / `currentParser` / `currentOptions` 保存当前连接，相当于后端的「内存状态」。
- **列举串口**（第 15–24 行）：`await SerialPort.list()` 调用系统 API 枚举硬件，对应前端「刷新端口列表」。
- **打开串口**（第 26–69 行，核心）：
  ```js
  currentPort = new SerialPort({ path, baudRate, dataBits, stopBits, parity, autoOpen: false })
  currentParser = currentPort.pipe(new ReadlineParser({ delimiter: '\n' }))
  ```
  - 用 `SerialPort` 真正打开硬件；
  - `.pipe(ReadlineParser('\n'))` 表示**按换行符分包**，即 README 中的 `ReadlineParser` 解析逻辑；
  - 收到数据时反向推给前端：
    ```js
    currentParser.on('data', (line) => {
      win.webContents.send('serial:data', {
        raw: line,
        hex: Buffer.from(line).toString('hex'),
        time: Date.now()
      })
    })
    ```
    `webContents.send('serial:data', ...)` 即后端 → 前端的「推送」（类似 WebSocket 的 server push）。
- **发送数据**（第 87–99 行）：把前端发来的字符串按编码转成字节流写入硬件，纯 Vue 做不到：
  ```js
  const buffer = encoding === 'hex'
    ? Buffer.from(data.replace(/\s/g, ''), 'hex')   // HEX 模式：转二进制
    : Buffer.from(data, 'utf8')                      // 文本模式
  currentPort.write(buffer, ...)
  ```

## 5. 安全桥梁：Preload

### 5.1 `src/preload/index.js` —— 前后端之间唯一的门

主进程规定 `nodeIntegration: false`，即前端界面碰不到 Node.js。前端要调串口，只能通过 preload 这个安全桥梁。

```js
import { contextBridge, ipcRenderer } from 'electron'

const api = {
  serial: {
    list:  () => ipcRenderer.invoke('serial:list'),
    open:  (options) => ipcRenderer.invoke('serial:open', options),
    close: () => ipcRenderer.invoke('serial:close'),
    send:  (data, encoding) => ipcRenderer.invoke('serial:send', data, encoding),
    onData:   (callback) => ipcRenderer.on('serial:data',   (_, payload) => callback(payload)),
    onStatus: (callback) => ipcRenderer.on('serial:status', (_, payload) => callback(payload)),
    onError:  (callback) => ipcRenderer.on('serial:error',  (_, message) => callback(message))
  }
}

contextBridge.exposeInMainWorld('electronAPI', api)
```

- `ipcRenderer.invoke('serial:open')` = 前端「打电话」给后端，字符串必须和主进程 `ipcMain.handle('serial:open', ...)` 完全一致（一对暗号）。
- **两个方向的方法有区别：**
  - `list/open/close/send` 用 `invoke`（前端主动问，后端答，有返回值）；
  - `onData/onStatus/onError` 用 `on`（后端主动推，前端被动收），对应 `serial.js` 里的 `webContents.send(...)`。
- `contextBridge.exposeInMainWorld('electronAPI', api)` 把这个 `api` 对象安全地挂到浏览器 `window` 上，于是前端可用 `window.electronAPI.serial.xxx`。
- **只暴露白名单里的 7 个方法，别的什么都碰不到** —— 这就是「最小暴露面」的安全设计（不暴露整个 `ipcRenderer`）。

### 5.2 `src/renderer/src/components/SerialPanel.vue` —— 前端如何使用接口

- **刷新端口列表**（第 31–43 行）：`ports.value = await window.electronAPI.serial.list()`
- **打开/关闭串口**（第 45–66 行）：把界面上选的参数打包发给后端 `open(...)`，由 `serial.js` 真正打开硬件。
- **监听后端推送**（第 72–81 行）：`window.electronAPI?.serial?.onStatus?.(...)` 和 `onError`，对应反向通道，用于更新绿点/「已连接」文字。

**完整链路：**

```
前端 SerialPanel.vue ──invoke──▶ preload ──IPC暗号──▶ 主进程 index.js
   (window.electronAPI.serial.open)        (ipcRenderer)      (ipcMain.handle)
                                                  │
                                          serial.js: new SerialPort() 真正打开硬件
                                                  │
                               webContents.send('serial:status'/'data')
                                                  ▼
                                        preload: onStatus/onData
                                                  ▼
                                          前端回调 → 更新 UI / 画波形
```

## 6. 数据如何变成波形

### 6.1 `src/renderer/src/components/ChartPanel.vue`

- **订阅数据流**（第 160 行）：`window.electronAPI?.serial?.onData?.(appendData)` 把 `appendData` 注册成回调，每来一行数据就调一次。
- **从文本抠数字**（第 35–38 行）：
  ```js
  function extractNumbers(text) {
    const matches = String(text).match(/[-+]?\d*\.?\d+/g)
    return matches ? matches.map(Number) : []
  }
  ```
  一行 `12.5 3.2 8.0` → `[12.5, 3.2, 8.0]`，对应 README「每行数据通过正则提取数字」。
- **数字塞进 8 条通道队列**（第 91–113 行，核心）：
  ```js
  function appendData(payload) {
    const values = extractNumbers(payload.raw)
    if (values.length === 0) return
    while (seriesData.value.length < values.length) seriesData.value.push([])
    values.forEach((v, i) => {
      seriesData.value[i].push(v)                 // 第 i 个数字 → 第 Ii 通道
      if (seriesData.value[i].length > maxPoints) seriesData.value[i].shift()  // 超 200 丢最旧
    })
    chart.setOption({ ... })                      // 告诉 ECharts 重画
  }
  ```
  - `seriesData` 是二维数组，`seriesData[i]` 即第 `Ii` 通道的历史队列；
  - **`maxPoints = 200` + `shift()` = README 的「滚动窗口（200 点）FIFO 队列」**：只保留最新 200 个，旧的从左被挤掉，波形从右往左滚动；
  - 最后 `chart.setOption(...)` 交给 ECharts 重绘。
- **ECharts 画成曲线**（第 40–82 行 `getChartOption`）：X 轴是采样点下标，Y 轴是数值（自动范围），`visibleChannels` 控制哪条线显示（点眼睛图标切换，`toggleChannel` 第 123–132 行）。

### 6.2 `src/renderer/src/components/DataMonitor.vue`

第 48–59 行**同样独立监听** `serial:data`，把数据以文本日志形式显示（Rx/Tx 方向、时间戳）。即「一份串口数据，多处消费」：波形图用于画图，数据流面板用于显示文本。

**数据变波形全景：**

```
设备发来 "12.5 3.2 8.0\n"
   │  主进程 ReadlineParser 分行 + send('serial:data')
   ▼
ChartPanel.appendData(payload)
   ├─ extractNumbers → [12.5, 3.2, 8.0]
   ├─ I0.push(12.5)  I1.push(3.2)  I2.push(8.0)   （超 200 则 shift）
   ▼
chart.setOption({ series: 各通道队列 })  →  ECharts 重绘折线
   ▼
屏幕出现随时间向右推进的实时波形
```

## 7. AI 助手如何调用大模型

### 7.1 `src/renderer/src/components/AiPanel.vue`

**关键前提：这一块完全不依赖 IPC / 主进程。** 它是渲染进程直接用浏览器原生 `fetch` 去请求大模型服务商服务器，自己就是一个标准 ChatGPT 风格客户端，和串口、主进程毫无关系。

- **配置来源**（第 7–11 行）：`apiKey` / `baseUrl` / `model` 直接存在浏览器 `localStorage`。默认值 `https://api.openai.com/v1`、`gpt-4o-mini`。因为 Base URL 可配，DeepSeek / 通义千问 / 任意 OpenAI 兼容接口都能用（改 Base URL 即可，协议完全一致）。改后 `saveConfig()`（第 31–35 行）立即写回 localStorage。
- **发送消息 + 构造请求**（第 37–58 行，核心）：
  ```js
  const response = await fetch(`${config.baseUrl}/chat/completions`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${config.apiKey}`
    },
    body: JSON.stringify({
      model: config.model,
      messages: messages.value.map(m => ({ role: m.role, content: m.content })),  // 整段历史
      stream: false
    })
  })
  ```
  - 请求地址 = `Base URL + /chat/completions`（OpenAI 聊天补全标准路径）；
  - 鉴权 = `Authorization: Bearer <API Key>`；
  - `messages` 传入**整个对话历史**，所以模型有记忆、能理解上下文（如「刚才那个波形」）；
  - `stream: false` = 整段生成完再一次性返回（非流式）。
- **解析返回 + 显示**（第 60–69 行）：标准结构 `data.choices[0].message.content`，用可选链 `?.` 防抖，失败则 push 一条「请求失败」。

**全景：**

```
AiPanel.vue（渲染进程，纯前端）
   ├─ 读 config（baseUrl/apiKey/model）
   └─ fetch(baseUrl + '/chat/completions')  ──HTTPS──▶  大模型云端
                                                        （OpenAI/DeepSeek/通义...）
   ◀── 返回 JSON ──  data.choices[0].message.content
   ▼
messages 数组 push → 气泡渲染到屏幕
```

## 8. 四条数据主线总结

| 主线 | 路径 | 经过主进程？ |
|------|------|------------|
| 串口配置/收发 | Vue → preload → IPC → serial.js | ✅ 是 |
| 波形绘制 | 主进程 `serial:data` → ChartPanel 正则提取 → ECharts | ✅ 是 |
| 数据日志 | 同上 → DataMonitor 显示文本 | ✅ 是 |
| **AI 对话** | **Vue 直接 fetch 云端，不经过 IPC** | ❌ 否 |

> 一句话：**串口链路（配置→收发→波形→日志）已端到端打通，是一条完整的 Electron 三进程架构；AI 模块目前是独立挂在窗口里的 ChatGPT 客户端。**

## 9. 当前项目的真实状态与发现的细节

### 9.1 AI 模块与串口数据是「断联」的
`AiPanel` 发请求时 `messages` 里只有用户打字内容，**没有把串口波形/数据喂给模型**。问「分析一下刚才的波形」，模型其实看不见波形，只能凭文字瞎猜。对应 README 待办：「串口数据注入到 AI 对话上下文 🔧 部分（待实现）」——这是项目 AI 能力目前最大的短板。

### 9.2 多处 UI 占位（印证 README 进度表）
- `SerialPanel.vue`：数据引擎 Raw/JustFloat、数据接口、AI 设置整块（模型、API Key、实时异常检测、协议自动识别）均 `disabled`，且 API Key 是写死的假值 `sk-***`。
- `DTR/RTS` 按钮只有样式无逻辑。
- `ChartPanel.vue`：Y 轴范围、X 轴范围输入框 `readonly`，网格线/十字准线开关 `disabled`。
- `DataMonitor.vue`：数据表子标签无内容；「AI 检测到数据异常」横幅是写死的静态文本，非真算。
- `AiPanel.vue`：快捷操作「数据分析/异常诊断/协议解析/发送指令」按钮无 `@click` 绑定，点击无反应。连接状态卡片 `COM3 @ 921600`、`Raw 协议` 均为静态文字。

### 9.3 发现的 Bug
- **`AiPanel.vue` 第 66 行拼写错误**：`'assitant'` 应为 `'assistant'`（少个 `s`）。导致错误消息不会被正确归类为 AI 消息，头像/边框样式错位，功能不受影响。

### 9.4 数据协议当前是「硬编码」
`extractNumbers` 用统一正则抓数字，默认假设「每行前 8 个数字 = I0~I7」。一旦未来支持 JustFloat（四字节浮点二进制），此处需替换为二进制解析逻辑——对应 README「Raw / JustFloat 协议引擎 🚧 占位」。
